In our previous expression proteomics workflow we described the processing steps required to prepare quantitative proteomics data for differential abundance analysis (Hutchings et al. 2023). Such preparation involved log2 transformation of the peptide-level quantitation data before aggregating to the protein level and normalising. These steps differ from those required when processing subcellular spatial proteomics data.

Quantitative proteomics data often undergoes logarithmic transformation prior to statistical analysis. The reason for this is that the majority of statistical tests require the data to display a normal distribution. Whilst raw quantitative MS-based proteomics data is dramatically skewed towards 0, the log2 transformed data is approximately normal. In this subcellular spatial proteomics workflow, however, the goal is not to prepare our data for downstream statistical differential abundance analysis. Instead, we are preparing the data for a machine learning classifier for which the input is protein correlation profiles across a biochemical gradient. The machine learning algorithm which we will use does not make the assumption that our data has a normal distribution, therefore we do not need to perform logarithmic transformation. In fact, logarithmic transformation would reduce the subcellular resolution by flattening our abundance distribution profiles.

The second data processing step which differs between expression and spatial proteomics analysis is that of normalisation. In most proteomics experiments the goal of normalisation is to remove any technological variation and account for experimental error. As a result, normalised data should contain near-identical samples in which the majority of variation is of biological importance. In spatial proteomics normalisation plays a different role because we are interested in the shape of protein abundance profiles rather than the magnitude of the intensity in each channel. Hence, the aim of normalisation here is to scale all of our quantitation data into the same space (within the range of 0 and 1) whilst maintaining the shape of our abundance profiles. If we did not do this, proteins with the same distribution across the gradient but different abundances would display very different profiles.

5.1 Normalisation

Based on De Duve’s principle (Duve 1964) we know that proteins which are co-localised within the cell will exhibit similar abundance distribution profiles across a fractionation gradient. This means that we we can infer the location of proteins by matching their abundance profiles to profiles of well-known organelle residents, termed “markers”. In order to get information about the abundance distribution of each protein across the fractionation gradient we need to carry out row sum normalisation. To do this we make use of the normalize function within the QFeatures infrastructure.

# Define number of replicates

Through the process of row sum normalisation we have now converted our raw quantitative values into a correlation profile or protein profile across the fractionation gradient. The abundance values represent the proportion of total quantification for each precursor that comes from each fraction, with each row sum being equal to 1. This scales all data into the same space so that we can use the shape rather than the intensity of profiles for downstream machine learning.

We can see from these plots that the raw precursor abundance values are spread across a wide dynamic range, spanning 7 orders of magnitude. This is very normal for cellular proteomics data. If we were to use the pre-normalised data, the profile of a high abundance protein would be numerically very different to that of a low abundance protein, even if they fractionate in the same pattern across our biochemical gradient. Once we normalise our precursors, all have an abundance between 0 and 1. We can now see some shape to the profiles.

Unlike in total proteome experiments where normalisation aims to remove variation, we do not expect the boxplots of normalised correlation profiles to be perfectly aligned. For each fraction, many proteins have low to 0 abundance. These are proteins that belong to organelles that primarily sediment elsewhere in the gradient. However, each fraction also has a long tail towards 1, indicating a subset of proteins that did predominantly pellet in this fraction. A box plot with shape and structure like this is a first indication that our experiment may have worked - we would not want a flat profile of boxplots.

NoteAt what stage should I normalise to generate profiles?

Before or after imputation? (Depends on extent of data missingness)

Some experimental designs yield a relatively low proportion of missing values, for example label-based methods that use TMT such as LOPIT. As a result, after an initial filtering step, there are very few values to impute. Applying a baseline k-NN imputation to such data can be more successful when the data are in a similar space after normalisation, as discussed in Hutchings et al. (2025). We note that by applying imputation after normalisation, the final imputed profiles will no longer sum to exactly 1. However, since such designs have such low missingness, the sum should not greatly exceed 1. By contrast, where datasets have a greater proportion of missing data to impute, as is the case for this example where we have a DIA LFQ design row sum normalisation of a limited number of fractions would generate a short profile summed to one and subsequent imputation could result in a correlation profile with an undesirably high sum value. Here it is necessary to impute prior to normalisation to ensure the generation of sensible correlation profiles in the same final space (between 0 and 1).

Before or after aggregation? (In practice, it makes little difference)

In this workflow we normalise each precursor profile to sum to 1 before aggregating to protein level. Precursors from the same protein can differ in raw intensity by orders of magnitude, mainly because they ionise differently, not because of the biology. If we aggregated raw intensities, a single very intense precursor could largely determine the protein’s profile.

For localisation, what matters is the shape of the profile across fractions, and each precursor is an independent measurement of that shape. Normalising first puts all precursors on the same scale, so each contributes equally to the protein profile. Aggregating with a median then gives a consensus profile that is robust to the occasional precursor with an unusual profile.

The trade-off is that low-intensity, noisier precursors are given the same weight as high-intensity ones. Our earlier intensity-based filtering helps by removing the weakest precursors. Because the median of profiles that each sum to 1 does not itself sum exactly to 1, we normalise once more after aggregation.

In practice, we find the order makes little difference to the resolution of the final spatial map. Either approach is reasonable, as long as the final protein profiles are normalised before downstream analysis.

5.2 Aggregation

Now that we have our final precursor-level dataset we can aggregate this upward to the protein level. The aim of this step is to combine data from all component precursors into a single protein-level entry. This entry will have one master protein accession and one quantitative value per biochemical fraction per sample.

Within the QFeatures infrastructure aggregation is carried out using the aggregateFeatures function. This function provides users with several options on how to aggregate multiple quantitation values into a single value. The methods differ with respect to how they deal with missing data as well as whether they require log2 or raw quantitation data as their input.

In our sister workflow Hutchings et al. (2023) we aggregate using robustSummary, a state-of-the-art aggregation method which is notably robust to outliers and missing values (Sticker et al. 2020; Goeminne et al. 2016). However, our data is not currently suitable for robustSummary aggregation as this method requires log2 transformed data. Whilst it would be relatively simple to log2 transform our quantitative data using the logTransform function within the QFeatures infrastructure, we would need to reverse this transformation by taking the exponential of the resulting protein data, which is not so simple. Instead we will aggregate precursors straight to protein level using colMedians method from the matrixStats package. We specify this method using the fun = argument, as well as telling the function which rowData column we wish to use for aggregation.

Here, we demonstrate one-step aggregation, from precursors directly to protein. This means aggregating all precursors with the same value of "Protein.Group". For an example of two-step aggregation, from precursor to peptide followed by peptide to protein, users are directed to Hutchings et al. (2023).

agg_names <- paste0("proteins_R", R)

qf <- QFeatures::aggregateFeatures(qf,
                                   i = norm_names,
                                   fcol = "Protein.Group", 
                                   name = agg_names,
                                   fun = matrixStats::colMedians)

5.2.1 Re-normalisation

Before aggregation, each precursor profile summed to 1. However, the median of several profiles that each sum to 1 does not itself sum exactly to 1. Let’s check the row sums of our protein-level data.

qf <- normalize(qf,
                i = agg_names,

5.3 Concatenating datasets for machine learning

Previous subcellular proteomics experiments utilising protein correlation profiles have benefited from the combining of datasets (Barylyuk et al. 2020; Christoforou et al. 2016; Moloney et al. 2023), that is the concatenation of replicates or experiments that utilise different gradients (Trotter et al. 2010). Since the use-case experiment included three biological replicates each with 9 biochemical fractions we can concatenate these data into a single dataset with 27 columns. In order to do this, the column names must be different in each replicate. By looking at the colnames of each experimental set per condition we verify we indeed have unique names.

5.3.1 Concatenation gives equal weight to all replicates

By concatenating the datasets we give each biological replicate an equal weight for the downstream machine learning classification. This means that any variability between experiments will be accounted for. For example, if a protein has an abundance distribution profile similar to that of nuclear protein markers in one of the three replicates, but is more similar to cytoplasmic markers in the remaining two replicates, this will be reflected by the fact that the protein will either be classified with a lower confidence or not classified at all. If each replicate was analysed separately, the protein may receive conflicting classifications in each replicate which would require a user-defined resolution.

Another potential advantage of concatenating datasets is the inclusion of data derived from different gradient variations (Barylyuk et al. 2020; Trotter et al. 2010). Although many subcellular compartments are well resolved using a single gradient, some compartments remain more challenging to resolve due to their similarities or connections with other compartments. For example, compartments within the endomembrane system can generate similar fractionation profiles. Where no single gradient will provide optimal separation of all organelles of interest, it is possible to design different gradients which provide optimal separation different organelles. These data can then be concatenated to generated a combined dataset with greater final resolution of all desired compartments.

Overall, data concatenation has been shown to have benefits for downstream machine learning in many cases. Ultimately, however, the decision to concatenate replicates will depend on the goal of the experiment and type of data analysis required to answer the experimental question. In particular, where the experimental aim is to identify differential localisation between conditions it is recommended to repeat the same biochemical gradient across all three replicates to avoid complicating downstream analysis.

5.3.2 Keeping track of peptide support and missing values

Before we move on, we record two pieces of information about the quality of each protein profile, so that we can use them later when interpreting our spatial maps:

  1. Peptide support: the number of precursors used to calculate each protein profile. Proteins quantified from only one or two precursors tend to have noisier profiles. aggregateFeatures recorded this in a rowData column called .n.
  2. Missing values: how much of each profile was imputed. In the previous lesson we recorded the number of missing values per precursor, before imputation, in a rowData column called nNA. Proteins whose precursors had many missing values rely more heavily on imputation and should be interpreted with more caution.

Neither of these makes it through to the joined set. aggregateFeatures does not carry nNA up to the protein level, and joinAssays only keeps rowData columns that are identical in every set, which .n is not.

We have written a small function, addProfileQC(), that summarises these to the protein level for each replicate and adds them to the joined set. For each protein it calculates the proportion of its precursor values that were missing before imputation, and then adds the following columns to the joined set:

  • n_rep1, n_rep2, n_rep3: number of precursors in each replicate
  • n_min, n_mean: minimum and mean across replicates
  • missing_rep1, missing_rep2, missing_rep3: proportion of values missing before imputation in each replicate
  • missing_max, missing_mean: maximum and mean across replicates

We report the minimum peptide support and maximum missingness because a protein profile is only as good as its weakest replicate.

## addProfileQC()
##
## Records two indicators of protein profile quality in a QFeatures object
## and carries them through to the joined (concatenated) set:
##
##   - peptide support: the `.n` column added by aggregateFeatures()
##   - missingness: the proportion of precursor values that were missing
##     before imputation, calculated from the per-precursor `nNA` column
##
## Both are lost by joinAssays(), because they differ between replicates.
##
## Arguments
##   qf          a QFeatures object
##   prec_sets   named character vector of precursor-level sets that carry `nNA`
##   prot_sets   named character vector of protein-level sets that carry `.n`
##               (same names and order as prec_sets, e.g. rep1, rep2, rep3)
##   joined_set  name of the joined protein-level set
##   group_col   rowData column linking precursors to proteins
##
## Adds to each protein-level set:
##   prop_missing
## Adds to the joined set:
##   n_<rep>, n_min, n_mean, missing_<rep>, missing_max, missing_mean
##
## Returns the updated QFeatures object.

addProfileQC <- function(qf,
                         prec_sets,
                         prot_sets,
                         joined_set = "proteins_joined",
                         group_col = "Protein.Group") {

  stopifnot(identical(names(prec_sets), names(prot_sets)))
  reps <- names(prot_sets)
  joined_ids <- rownames(qf[[joined_set]])

  for (r in reps) {
    prec <- prec_sets[[r]]
    prot <- prot_sets[[r]]
    rd <- rowData(qf[[prec]])

    ## Proportion of missing values per protein:
    ## total missing values / (number of precursors x number of fractions)
    tot_na <- tapply(rd$nNA, rd[[group_col]], sum)
    tot_values <- tapply(rd$nNA, rd[[group_col]], length) * ncol(qf[[prec]])
    prop <- tot_na / tot_values

    ## Add to the protein-level set of this replicate
    rowData(qf[[prot]])$prop_missing <-
      as.numeric(prop[rownames(qf[[prot]])])
  }

  ## Extract a rowData column from each replicate, matched to the joined set
  per_rep <- function(col, prefix) {
    m <- sapply(prot_sets, function(s) {
      rd <- rowData(qf[[s]])
      rd[[col]][match(joined_ids, rownames(rd))]
    })
    m <- matrix(m, ncol = length(prot_sets))
    colnames(m) <- paste0(prefix, reps)
    m
  }

  n_mat <- per_rep(".n", "n_")
  miss_mat <- per_rep("prop_missing", "missing_")

  ## Per-replicate values plus summaries across replicates
  qc_df <- DataFrame(n_mat,
                     n_min = apply(n_mat, 1, min),
                     n_mean = rowMeans(n_mat),
                     miss_mat,
                     missing_max = apply(miss_mat, 1, max),
                     missing_mean = rowMeans(miss_mat))

  rowData(qf[[joined_set]]) <- cbind(rowData(qf[[joined_set]]), qc_df)

  qf
}

                   prec_sets = c(rep1 = "norm_precursors_R1",

                   prot_sets = c(rep1 = "proteins_R1",

TipKey Points
  • Spatial proteomics data are prepared for machine learning on profile shape, not for statistical tests, so log transformation is not needed and would flatten the profiles.
  • Row-sum normalisation turns raw intensities into profiles that sum to 1. This puts all features on the same scale while preserving the shape of their distribution across the gradient.
  • For sparse label-free data, impute before normalising, so that profiles are complete before they are scaled.
  • Aggregation combines precursors into one profile per protein group. The aggregation method must match the data: robustSummary needs log-transformed input, whereas colMedians can be used on normalised profiles directly.
  • Whether you normalise before or after aggregation makes little practical difference, as long as the final protein profiles are normalised.
  • aggregateFeatures() and joinAssays() only keep rowData columns that are the same for every feature being combined, so per-replicate quality information, such as the number of precursors (.n) and the proportion of missing values, must be summarised and added back to the joined set.
  • Concatenating replicates with joinAssays() gives each replicate equal weight in classification, so inconsistent proteins are classified with lower confidence rather than given conflicting labels.
  • Concatenation can also combine different gradients to improve resolution. For differential localisation between conditions, however, the same gradient should be used across all replicates.
